# Validating the shared Neuron compile cache

How to deploy this and prove the optimisation does what it claims. Three levels,
in increasing cost and confidence:

| Level | Proves | Needs |
|---|---|---|
| [1. Storage layer](#level-1-the-shared-cache-works) | a cache written on one node is usable from another | two nodes |
| [2. Storage cost](#level-2-what-the-shared-cache-costs) | cache retrieval is cheap next to a compile | two nodes |
| [3. Serving](#level-3-startup-time-with-and-without-a-warm-cache) | actual vLLM startup saved | Neuron node, HF token |

Levels 1 and 2 need no Hugging Face token and no Neuron device. Level 3 is the
end-to-end proof and is the one that produces a number you can publish.

## Deploy

Follow [README.md](README.md). In short:

```bash
./bootstrap-efs.sh --dry-run    # inspect; no config file needed
./bootstrap-efs.sh
oc apply -f ../argocd/applicationset-performance.yaml
```

### Confirm each layer

```bash
# Applications generated by the cluster generator and converged
oc get applications -n openshift-gitops
```

Expect `Synced` / `Healthy` for `<cluster>-efs-storage` and
`<cluster>-neuron-operator`, plus `<cluster>-oai-hardened` if `enable_oai=true`.
They are independent and converge in any order; a PVC created before the driver
is ready simply stays `Pending` and binds later.

```bash
# EFS CSI driver actually installed, not just subscribed
oc get clustercsidriver efs.csi.aws.com -o json \
  | jq -r '.status.conditions[] | select(.status=="True") | .type' | grep Available
```

Expect `AWSEFSDriverControllerServiceControllerAvailable` and
`AWSEFSDriverNodeServiceControllerAvailable`.

```bash
# STS wiring: the ROLEARN on the Subscription became a usable credential
oc get secret aws-efs-cloud-credentials -n openshift-cluster-csi-drivers \
  -o jsonpath='{.data.credentials}' | base64 -d
```

Expect a `role_arn` and `web_identity_token_file`. If this secret is missing, the
role ARN never reached the operator and every PVC will stay `Pending`.

```bash
oc get sc efs-sc
oc get nodes -o custom-columns=NAME:.metadata.name,NEURON:.status.allocatable.aws\\.amazon\\.com/neuron
```

The Neuron node should advertise a non-zero device count once the operator has
built and loaded the kernel module.

## Level 1: the shared cache works

This is the property everything else rests on. `ReadWriteOnce` would confine the
cache to a single node, so scale-out and rescheduling would recompile.

```bash
oc apply -f tests/rwx-share-test.yaml
oc wait --for=condition=Ready pod/cache-writer -n neuron-cache-test --timeout=180s
oc logs -f pod/cache-reader -n neuron-cache-test
```

Expect:

```
SHARED-CACHE-OK  read and wrote an 8MB artifact produced on <other-node>
```

The reader uses pod anti-affinity to land on a different node from the writer,
and fails loudly with `SHARED-CACHE-INCONCLUSIVE` if it does not. It also appends
to the file, because a cache has to be writable from every node rather than only
readable. Different availability zones is opportunistic rather than asserted; if
you get one, both mount targets have been exercised.

Leave the namespace in place if you want to run level 2, otherwise:

```bash
oc delete -f tests/rwx-share-test.yaml
```

## Level 2: what the shared cache costs

EFS is NFS, and a compile cache is many small files, so it is fair to ask whether
reading it back is slower than recompiling. Measure it:

```bash
oc apply -f tests/storage-latency-probe.yaml
oc wait --for=jsonpath='{.status.phase}'=Succeeded pod/storage-latency-probe \
  -n neuron-cache-test --timeout=300s
oc logs pod/storage-latency-probe -n neuron-cache-test
```

Measured on ROSA 4.22.11 (`inf2.8xlarge`, elastic throughput, generalPurpose):

```
LOCAL(emptyDir)    write300x32k=  515ms  readAll300=    8ms  write256MB= 1185ms  read256MB=   27ms
EFS(RWX)           write300x32k= 5598ms  readAll300=  716ms  write256MB=  846ms  read256MB=  608ms
```

Read the absolute numbers. Per-file overhead on EFS is real, and the local reads
are served from page cache so they flatter local disk. What matters is that
retrieving a cache takes well under a second here, against a compilation measured
in minutes. That is why this chart mounts EFS directly instead of copying into a
local `emptyDir` at startup.

## Level 3: startup time with and without a warm cache

This is the only level that answers "how much faster does vLLM start". Nothing
below has been measured yet in this repo, so treat the procedure as the
instrument and record your own numbers.

### Prepare

Enable the OpenShift AI layer and cache the model weights, so that weight
download is not part of what you are timing. Without this you measure download
plus compile together and cannot attribute the saving.

```bash
oc create secret generic hf-token \
  --from-literal=HF_TOKEN=<token> -n neuron-inference

SECRET=$(oc get secret -n openshift-gitops -l neuron_perf=true -o name | head -1)
oc label $SECRET -n openshift-gitops enable_oai=true --overwrite
```

Then set `modelCache.enabled=true`, `modelCache.download.enabled=true` and
`model.source=pvc` in `deploy/helm/oai-hardened/values.yaml` and commit, which is
where all model configuration lives. Wait for the download Job to finish:

```bash
oc wait --for=condition=complete job/neuron-model-cache-download \
  -n neuron-inference --timeout=3600s
```

### Run A: cold cache

Ensure the compile cache is empty. The cleanest way is to recreate the PVC, since
deleting it releases the EFS access point:

```bash
oc delete pvc neuron-compile-cache -n neuron-inference   # ArgoCD recreates it
```

Then bring up the InferenceService and time it:

```bash
time_to_ready() {
  ns=$1; isvc=$2
  pod=$(oc get pods -n "$ns" -l serving.kserve.io/inferenceservice="$isvc" \
        -o jsonpath='{.items[0].metadata.name}')
  start=$(oc get pod "$pod" -n "$ns" -o jsonpath='{.status.startTime}')
  ready=$(oc get pod "$pod" -n "$ns" \
          -o jsonpath='{.status.conditions[?(@.type=="Ready")].lastTransitionTime}')
  echo "pod=$pod start=$start ready=$ready"
  python3 - "$start" "$ready" <<'PY'
import sys, datetime
f="%Y-%m-%dT%H:%M:%SZ"
a=datetime.datetime.strptime(sys.argv[1],f)
b=datetime.datetime.strptime(sys.argv[2],f)
print(f"time to Ready: {(b-a).total_seconds():.0f}s")
PY
}

oc wait --for=condition=Ready inferenceservice/llama31-8b-neuron \
  -n neuron-inference --timeout=3600s
time_to_ready neuron-inference llama31-8b-neuron
```

Confirm this run actually compiled, and that it populated the cache:

```bash
oc logs -n neuron-inference -l serving.kserve.io/inferenceservice=llama31-8b-neuron \
  --tail=-1 | grep -i "compil"
```

### Run B: warm cache

Delete the pod but keep the PVC, so the next pod finds the cache populated:

```bash
oc delete pod -n neuron-inference -l serving.kserve.io/inferenceservice=llama31-8b-neuron
oc wait --for=condition=Ready inferenceservice/llama31-8b-neuron \
  -n neuron-inference --timeout=3600s
time_to_ready neuron-inference llama31-8b-neuron
```

Evidence of a cache hit. The Neuron SDK logs a line of this form when it reuses a
compiled artifact instead of building one:

```bash
oc logs -n neuron-inference -l serving.kserve.io/inferenceservice=llama31-8b-neuron \
  --tail=-1 | grep -i "cached neff\|Compile cache path"
```

### Run C: a different node

The saving that matters for scale-out is on a node that has never compiled this
model. Cordon the node that ran B, delete the pod, and let it reschedule:

```bash
oc cordon <node-that-ran-B>
oc delete pod -n neuron-inference -l serving.kserve.io/inferenceservice=llama31-8b-neuron
# wait for Ready, then
time_to_ready neuron-inference llama31-8b-neuron
oc uncordon <node-that-ran-B>
```

Run C is the number to publish. It is the case a `ReadWriteOnce` cache cannot
help with, and the reason this deployment uses `ReadWriteMany`.

### Interpreting it

Record all three:

| Run | Cache | Node | Time to Ready |
|---|---|---|---|
| A | cold | any | |
| B | warm | same as A | |
| C | warm | never compiled | |

What the cache removes is compilation. What remains in every run is image pull,
Neuron runtime and device init, weight load, and vLLM engine startup, so B and C
will not approach zero. If B is not meaningfully below A, check that
`NEURON_COMPILE_CACHE_URL` is set in the runtime and that `NEURON_CC_FLAGS
--cache_dir` is not overriding it, since `--cache_dir` takes precedence.

Note also that `servingRuntime.probeInitialDelaySeconds` defaults to 900, sized
for a cold start. Once you know the warm number, lowering it is what turns a
faster start into a faster rollout, because the readiness probe otherwise gates
when traffic is admitted.

`deploy/examples/oai-inference/README.md` states roughly 30 minutes cold and 5
minutes warm. That figure is unsourced in this repo and predates these charts;
this procedure exists to replace it with something measured.

## Teardown

```bash
oc delete -f tests/rwx-share-test.yaml            # includes the test namespace
oc delete -f ../argocd/applicationset-performance.yaml
oc delete secret -n openshift-gitops <cluster>-neuron-perf
```

The EFS filesystem, mount targets, security group, IAM role and policy are not
managed by GitOps and survive on purpose, so an uninstall cannot destroy a warm
cache. Remove them with `aws` when you mean to.
